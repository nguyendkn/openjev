## Unresolved Gaps

- [ ] **G21 (new, correctness/safety)**: `LayaNative::score()` (`lib.rs:71-137`) computes `k = built.markers.len()` and later reads `raw: Vec<f32> = (0..k).map(|i| *p.add(i))` straight out of `g.logits`, a ggml tensor allocated with exactly `kmax = w.max_opts` (16) elements. Nothing clamps `k` to `max_opts` before that read. `w.temperature()`'s own bucket logic (`"11+"` size bucket) implies >10-option questions are an anticipated real input shape; if a caller ever passes >16 options, this reads past the end of the `logits` tensor's buffer — a genuine raw-pointer OOB read (undefined behavior / potential segfault), not a resource leak. Not triggered by any current test (all exercise k=2). Fix: `let k = built.markers.len().min(self.w.max_opts);` before building `raw`, or reject/truncate earlier in `build_sequence`.
- [ ] **G22 (new, resource leak)**: `Weights` (`gguf.rs`) and `Graph` (`graph.rs`) hold raw `*mut gguf_context`/`*mut ggml_context` with no `Drop` impl calling `gguf_free`/`ggml_free`. Every new sequence-length bucket (`LayaNative::graph_for`) permanently leaks its entire arena for the process lifetime — the arena is sized `per_layer*32*2 + 512MiB` per bucket (hundreds of MB), ×4 buckets in the benchmark loop alone. Harmless in this loop's short-lived probe/test usage; will matter once Loop 12 wires this into the long-lived `openjev-server` process. Fix: add `Drop` impls.
- [ ] **G23 (new, fragile-but-working)**: `Graph::build`'s arena size (`graph.rs:70-74`) is explicitly commented as a "Rough upper bound," not a verified one — `ggml_init`'s null-check only catches failure of the top-level buffer allocation, not the arena being undersized for the actual graph's node count/intermediate sizes (ggml's bump allocator can silently write past an undersized buffer depending on build/assert config — this is exactly the "segfault/UB if wrong" class the Runtime asked about). It worked without any visible failure across all 4 tested buckets (64/128/256/512, incl. the extra real+temp-head ops) this loop, so not a proven bug, but it's unverified-by-construction. Recommend an explicit `ggml_used_mem(ctx)` vs `mem_size` assertion after `ggml_build_forward_expand` rather than relying on the heuristic being enough, especially before Loop 11 adds more head ops.
- [ ] **Probability/confidence gap root cause still open**: measured P(B)=0.5987 vs reference 0.586 (~1.3pp), confidence 0.0283 vs 0.0215 (~32% relative). I independently re-derived every one of D_10's structural claims against `graph_spec.json` ground truth (layer-0 no-norm, LN-fold 60/62 vs 2/62, RoPE theta/pattern, relu-block scope, tensor-name-to-node mapping) and found **no logic bug** — everything checked out exactly as claimed. Two remaining, un-ruled-out explanations: (a) Q8_0 dequant + F16 flash-attention numeric accumulation across 30 total layers (28 encoder + 2 head), never compared against an F32/reference-precision path this loop; (b) an unverified subtlety in the *temporary* head+scorer (D_10 itself flagged Task 6's validation as inherently limited — no intermediate-tensor comparison was available, only the final end-to-end probability ballpark). Cannot distinguish (a) from (b) without Loop 11's planned `ggmlc-dbg` layer-by-layer diff at `/tmp/ggmlc-dbg` (Runtime-approved, separate from `/tmp/ggmlc/build`). Do not treat this as closed; Runtime's "not enough to cutover, Loop 11 must find root cause" decision is correct and independently supported by this audit.
