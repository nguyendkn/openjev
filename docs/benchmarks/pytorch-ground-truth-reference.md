# PyTorch Ground-Truth Reference — unquantized `DecisionModel`, H100, float32

**What this file is.** Output distributions from the **ORIGINAL unquantized PyTorch
implementation** of Laya (`laya/common.py`'s `DecisionModel`, `laya/agent.py`'s `Agent.system_one`
from `github.com/NandhaKishorM/laya`), loaded from `convaiinnovations/laya`'s **fp32 safetensors
master weights**, executed on an **NVIDIA H100 80GB HBM3**.

**This is the true mathematical reference, not a quantized reimplementation.** Every other number
this project has ever recorded for Laya — production `laya serve` (`ggmlc` C++, Q8_0 GGUF, `-O0`
and `-O3`) and `crates/laya-native` (Rust + raw `ggml`, Q8_0 GGUF) — is a *quantized* approximation
of what is recorded here. When a build disagrees with this file, this file is right by definition
and the build has drifted.

Generated by Loop 15 on the K8s GPU cluster (`fke-ncp-modas-stg-qc8ifaxe`, namespace `llms-lab`),
not on the production CPU server. No production resource was touched to produce it.

Two precisions are recorded for every scenario:

* **`fp32`** — no autocast. The reference.
* **`bf16`** — `torch.autocast(bfloat16)`, which is what the shipped `Agent` actually runs on an
  H100 (`rl_agent_config.json` has `amp_dtype: "bf16"`, and `Agent.__init__` keeps bf16 for
  compute capability >= 8). Recorded because it is the *shipped* GPU default, and — see the
  comparison below — it turns out to be what the `-O3` C++ build tracks most closely.

Every scenario was run 4x (1 warmup + 3 measured); `deterministic_across_3_runs` is `true` for
all 15 scenarios in both precisions, so none of the numbers below are single-sample noise.

## Two temperature policies, both recorded

`rl_agent_config.json` ships `temperature_by_options["choice:11+"] = 0.1006`. The **upstream
Python** refuses it: `laya/common.py` defines `TEMP_MIN = 0.5 / TEMP_MAX = 5.0` and
`clamp_temperature()`, with a source comment stating outright that a 0.1006 temperature "multiplies
[the logits] ~10x: a 0.24 top probability is published as 0.99, so a caller gating on confidence is
told a coin flip is a certainty. No honest calibration needs to sharpen this hard, so refuse to
apply one that does." Loading the checkpoint emits a `RuntimeWarning` naming the rejected bucket.

`ggmlc`'s C++ `laya` and `crates/laya-native` both apply `max(t, 1e-3)` instead, i.e. they use the
raw 0.1006. So:

* `probabilities_clamped` / `confidence_clamped` — **upstream Python semantics**, `[0.5, 5.0]`.
* `probabilities_raw` / `confidence_raw` — **`ggmlc` / `laya-native` semantics**, `max(t, 1e-3)`.

The two policies are **identical for every `k <= 10` question** (all 10 project benchmark scenarios),
and diverge only in the `choice:11+` bucket — which is exactly the bucket Loop 11 changed. See
"Temperature-clamp reversal" below.

`logits` are policy-independent and precision-annotated; they are the most robust thing in this
file to diff a reimplementation against.

### Verdict: `-O3` is the correct reference target — now proven, not assumed

Loops 11 and 12 *assumed* `-O3` was "more correct" than `-O0` because `-O3` matched the debug
rebuild. That was circular: both were the same C++ code. Scenario 10 is the only scenario where the
two C++ builds disagree, and it settles it against an independent reference:

| build | approve | approve-with-conditions | deny | confidence | delta vs PT fp32 (top) |
|---|---|---|---|---|---|
| **PyTorch fp32 (ground truth)** | **0.8539** | **0.1365** | **0.0096** | **0.5890** | — |
| PyTorch bf16 (shipped GPU default) | 0.8554 | 0.1350 | 0.0097 | 0.5915 | 0.0015 |
| C++ `-O3` (current production) | 0.8559 | 0.1342 | 0.0099 | 0.5917 | 0.0020 |
| C++ `-O0` (pre-Loop-12 production) | 0.8365 | 0.1533 | 0.0102 | 0.5599 | 0.0174 |

`-O3` is **8.7x closer to ground truth than `-O0`** on the one scenario that separates them, and
its full vector (`0.8559 / 0.1342 / 0.0099`, confidence `0.5917`) is within **0.0005** of PyTorch's
shipped-bf16 path (`0.8554 / 0.1350 / 0.0097`, confidence `0.5915`). `-O0`'s `0.8365` is the
outlier. **Loop 11/12's assumption was correct, and this is the first evidence for it that does not
come from the same C++ source tree.** Keep targeting `-O3`.

### Where `crates/laya-native` stands

`crates/laya-native`'s own per-scenario probability vectors were **never written to a file in this
repo** — Loop 11 recorded only the prose claim that it matches the `-O3` build (`7/7` correct
choice, "<1e-4 on the exact case, most within tiny epsilon" across the scenarios) and Loop 10's
`0.599` pre-fix number for the reference case. So `laya-native` cannot be given an independent
column here without re-running it, which is out of this loop's scope (`crates/laya-native` is
explicitly not to be touched). What can be said from the recorded numbers:

| build | reference case `B` (capital of France) | delta vs PT fp32 |
|---|---|---|
| **PyTorch fp32 (ground truth)** | **0.6110** (conf 0.0358) | — |
| PyTorch bf16 | 0.6072 (conf 0.0334) | 0.0038 |
| `laya serve` Q8_0 production (`-O0` and `-O3` agree here) | 0.5860 (conf 0.0215) | 0.0250 |
| `crates/laya-native`, Loop 10 (pre-fix, had real bugs) | 0.5990 | 0.0120 |
| `crates/laya-native`, Loop 11 (post-fix, matches `laya serve` to <1e-4) | ~0.5860 | ~0.0250 |

Reported honestly because it complicates the record: **Loop 11's fixes moved `laya-native` from
0.0120 to ~0.0250 away from the PyTorch ground truth on this case.** That is not a regression in
`laya-native` — its goal was bit-parity with `ggmlc`, which it achieved, and Loop 10's closer number
came from buggy code that happened to land nearer. But it does mean *every* Q8_0 GGUF build,
including `laya-native`, carries a systematic ~0.025 probability offset from the real model on this
case that no amount of matching `ggmlc` will remove. Closing that would require a different
quantization of the weights, not a different graph — see the next section.

### The Q8_0 GGUF gap is real and is NOT explained by weight quantization alone

Largest ground-truth-vs-production gaps: `8_adversarial_ambiguity` **0.0290** (PT 0.9240 vs C++
0.8950) and `6_content_moderation` **0.0247** (PT 0.5583 vs C++ 0.5830), plus 0.0250 on the
reference case. But a numerical simulation of GGUF Q8_0 *weight* quantization against these exact
fp32 weights (next section) drifts the top probability by only **0.0035 mean / 0.0162 max**. So
roughly half to two thirds of the observed production gap comes from something other than weight
quantization — most plausibly `ggml`'s **activation** re-quantization to Q8 at each matmul plus
fp16 flash-attention accumulation, neither of which the weight-only simulation models. Recorded as
a bounded, characterized offset rather than an unexplained discrepancy.

**All three `11+` cases pick the correct option and are numerically stable at k=11/17/20** — no
sign of the out-of-bounds `k` read G21 fixed, and the sequence builder's option-budget truncation
branch (`opt_budget < 16`) was not triggered even at k=20 (121 tokens, well inside
`head_max_len=192`).

**The reversal Loop 11 needs to know about.** Loop 11 recorded, as one of three root causes it
fixed, "a REAL logic bug — our temperature clamp `[0.5, 5.0]` was wrong, the reference only clamps
to `max(t, 1e-3)`". Against `ggmlc` that is true. Against the **original PyTorch reference it is
backwards**: `laya/common.py` has `TEMP_MIN = 0.5`, `TEMP_MAX = 5.0` and `clamp_temperature()`
verbatim, and `Agent.__init__` applies it to every bucket while warning the user about the rejected
one. `crates/laya-native`'s *original* `[0.5, 5.0]` clamp matched upstream Python exactly; Loop 11
removed it to match the C++ reimplementation, which upstream deliberately disagrees with.

The numbers make the consequence concrete. On `E1_11opt_bucket_11plus` the correct option wins
either way, but the reported confidence goes from **0.9642** (upstream clamped) to **1.0000**
(raw) — the raw policy publishes certainty on a question where the fp32 model's own distribution
still carries entropy. This is exactly the failure mode the upstream source comment describes.

This is a **specification conflict, not a bug in either build**: `ggmlc` and upstream Python
genuinely disagree about `choice:11+`, and both behaviours are recorded above so a future loop can
pick a side deliberately. Deciding which one `crates/laya-native` should follow is out of scope
here (that crate is not to be touched this loop). Note it only ever matters for k >= 11; all 10
project benchmark scenarios are unaffected.

## Task 8 (exploratory): would a different quantization scheme be worth trying on CPU?

Weight-only fake-quant (quantize -> dequantize -> run fp32) applied to all **122 `nn.Linear`
weight tensors / 363.3M parameters** of the real fp32 checkpoint, evaluated on all 15 scenarios
against the fp32 baseline. This isolates *weight* quantization error from everything else.

| scheme | description | choice agreement | mean \|dP\| | max \|dP\| | mean d(top prob) |
|---|---|---|---|---|---|
| `q8_0_blk32` | GGUF Q8_0: per-block-32 symmetric int8 (**today's production quant**) | 15/15 | 0.00407 | 0.01622 | 0.00354 |
| `int8_chan` | per-output-channel symmetric int8 (no blocking) | 15/15 | 0.00745 | 0.03755 | 0.00721 |
| `q4_grp128` | AWQ/GPTQ-style: group-128 symmetric int4 | 12/15 | 0.07325 | 0.31796 | 0.06645 |
| `q4_0_blk32` | GGUF Q4_0: per-block-32 symmetric int4 | 12/15 | 0.09425 | 0.53179 | 0.09393 |
| `int4_chan` | per-output-channel symmetric int4 | 14/15 | 0.10317 | 0.35931 | 0.08931 |

**Answer: no — INT4/AWQ-style quantization is not worth trying on the CPU engine.** All three
4-bit schemes flip the winning option on real scenarios (`q4_0_blk32` and `q4_grp128` flip 3 of 15,
`int4_chan` flips 1 of 15) and move probabilities by 0.07-0.10 mean / 0.32-0.53 max — one to two
orders of magnitude worse than the ~0.008 gap this whole investigation is about. `q4_0_blk32`
collapses `4_agent_tool_routing`'s top probability from 0.6751 to 0.1433 and flips
`2_jailbreak_detection` and `9_compliance_gating`, the two security/compliance-gating scenarios.

**Q8_0 — what production already runs — is the right choice and is already near-optimal**: 15/15
choice agreement and 0.0035 mean top-probability drift, better than even per-channel int8
(0.0072), because Q8_0's 32-element blocks track local weight-magnitude variation more tightly
than one scale per output channel. There is no accuracy headroom to reclaim by changing the weight
quantization scheme; the remaining gap to ground truth lives in activation quantization and
attention accumulation, not in the weights.

This was exploratory per D_15 Task 8 and is a *numerical* result only — no CPU-side speed
measurement was made, and no change to `crates/laya-native` is proposed here.
